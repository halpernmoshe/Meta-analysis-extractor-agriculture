# Stage 2: conversion into canonical key tables

Both sides are converted into the same table format before any comparison: one CSV per paper, one
row per observation, with categorical key fields and the reported means. The analyses in
`3_evaluation/` and `4_figures/` read only these tables. The `gt` folders hold the
published-reference tables (`gt` is a historical file label).

What re-runs: the AI-side tables are rebuilt from the extraction records by the five decoders. The
reference-side tables are rebuilt from the published files for Loladze, Li J and Hui (Hui needs the
workbook to be downloaded) and for Boldorini (with two documented rows that differ in `crop` and
`evidence`). The Biochar reference tables cannot be rebuilt by a script; each of their rows is traced
to the published file. Details are in `reference_side/README.md`.

## Running a decoder

```bash
python 2_conversion/ai_side/decode_loladze.py
```

Output goes to `generated_keys/` at the repository root, or to the folder named by the environment
variable `DECODER_OUTPUT_ROOT`. The deposited tables in `keys/` are never overwritten. On Windows, set
`PYTHONIOENCODING=utf-8` before running `decode_li_j.py` without `--quiet`; its progress listing
contains non-ASCII author names that the default console encoding cannot print.

The AI-side tables regenerated by the decoders are content-identical to the deposited
`keys/<dataset>/ai/` tables after line-ending normalisation. The comparison ignores only the
difference between CRLF and LF line endings.

## Table format

Each key table has these columns: `row_id`, `side`, `paper_id`, `outcome_canonical`, `crop`,
`treatment_level`, `co_amendment`, `co_amendment_level`, `timepoint`, `aggregation_level`,
`unit_canonical`, `control_token`, `treatment_mean`, `control_mean`, `source_locator`, `is_figure`,
`evidence`, `decoder`. The means are used only to score rows that are already paired. `evidence` is a
short audit quote.

`treatment_level`, `co_amendment`, `co_amendment_level` and `timepoint` are generic slots. Each
decoder places its corpus's own design coordinates in them, so a column name does not mean the same
thing in every dataset. For the biochar dataset they hold the biochar dose and the co-applied
amendment. For Loladze 2014 they hold the element (`treatment_level`, for example ca, fe, zn, n), the
plant tissue (`co_amendment`) and the cultivar (`co_amendment_level`). Both sides of a dataset use the
same slots, so pairing compares like with like.

## Steps that use the other side

Decoding is done separately for each side, but some steps read identifiers from the other side.
Two AI-side decoders read the reference key tables, and both uses are documented in their ledgers:

- `decode_li_j.py` reads the reference paper-identifier vocabulary to crosswalk AI paper files to
  reference paper identifiers. (The analysis scripts add a second, author-and-year crosswalk for
  reference rows labelled only by study number; two same-author, same-year reference studies,
  `gt_study08` and `gt_study146`, are left unmatched there after a check of source titles.)
- `decode_boldorini_march_v11.py` reads the reference's structural treatment-token form.

On the reference side, the Loladze, Li J and Boldorini builders contain hand-written crosswalks that
map published studies to the corpus paper identifiers, and the Hui builder takes its list of papers
from the AI-side key-table file names. Some Boldorini overrides were chosen to align tokens with the
AI-side keys, as their comments state. These tables are listed in `reference_side/README.md`.

## Path names in older files

The decoder ledgers and some comments inside the decoders use the previous folder names:
`source_records/` is now `1_extraction/records/`, `runs/<dataset>/keys/` is now
`2_conversion/keys/<dataset>/`, and `decoders/` is now `2_conversion/ai_side/`. Scripts and notes
that they name without a repository path (for example `gen_ai_keys.py`, `patch_iter0.py`,
`diagnosis_iter0.md`) are earlier project files and are not part of this repository.
